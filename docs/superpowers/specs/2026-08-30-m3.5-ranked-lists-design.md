# M3.5 — Ranked lists and priority hydration — Design

Date: 2026-08-30
Status: approved for implementation planning

M3 left the catalogue hydratable but barely hydrated. Counted live against Neon on
2026-08-30, immediately after the M3 merge:

```
steam_app:  game/pending 183,105   dlc/pending 61,893   game/ok 27
game 27 · game_media 327 · genre 11 · category 52 · price 8 · price_history 17 · review_summary 1
```

M4 cannot be built on that. Two things stand in the way, and they are the same thing seen
from two sides:

1. **Coverage.** 27 of 183,105 games are hydrated. A full pass at `STEAM_STOREFRONT_RPS=1.2`
   is roughly 42 hours of wall clock.
2. **Ordering.** M4 wants Discover, Specials, Coming Soon, New Releases and Top Sellers, but
   nothing in the schema or the three jobs produces a popularity ordering. `hydrate` walks
   the queue by `next_attempt_at`; `game.release_date` and `price.discount_percent` can order
   two of those rows, and nothing can order Top Sellers or choose a hero.

Both are solved by the same missing input: a ranked list of appids from Steam. That list
tells the browse rows what to show *and* tells hydration which few hundred appids are worth
fetching first. M3.5 builds it. It ships no UI — that remains M4.

---

## 1. Observed Steam behaviour

Everything in this section was called live on 2026-08-30 and the responses inspected. No
figure here is quoted from documentation or memory.

### 1.1 `store.steampowered.com/api/featuredcategories`

HTTP 200, `application/json`, no key required, called with `cc=cz&l=english`. Top-level keys:

```
0..6 (editorial buckets; 0 is cat_spotlight), specials, coming_soon, top_sellers,
new_releases, genres, trailerslideshow, status
```

Item counts: `specials` 10, `coming_soon` 10, `top_sellers` 10, `new_releases` 30. `genres`
is a label only — `{"id":"cat_genres","name":"Genres"}`, with no `items` key at all.

Items carry `id` (the appid), `name`, `original_price` / `final_price` as minor-unit
integers with `"currency": "EUR"` — consistent with the `cc=cz` → EUR finding in the main
design §1.2 — plus `discount_percent`, `discount_expiration`, platform flags, and
`small_capsule_image` / `large_capsule_image` / `header_image` as full URLs carrying the
per-app hash segment.

Enough for a hero and one shallow row. Too thin to fill grids, and it offers no way to ask
for more.

### 1.2 `api/featured`

`featured_win` / `featured_mac` / `featured_linux` at 10 items each; `large_capsules` was
empty at call time. Strictly weaker than §1.1 and not used.

### 1.3 `IStoreTopSellersService/GetWeeklyTopSellers`

HTTP 200 but a 15-byte body, `{"response":{}}`, on every variant tried: key alone, with
`country_code=CZ`, with `page_count=100`, and with the same arguments passed as `input_json`.
Not used. This is a failure to find the right parameters, not evidence that the method is
unusable — if a deeper ranked list is ever wanted, it is worth another look.

### 1.4 `store.steampowered.com/search/results/` with `infinite=1`

The endpoint M3.5 is built on. Returns `application/json`:

```json
{ "success": 1, "results_html": "…", "total_count": 2481, "start": 0 }
```

`results_html` is store markup, one `search_result_row` per result, each carrying
`data-ds-appid` and a `<span class="title">`. Observed with `category1=998` and
`count=50`:

| query | `total_count` |
|---|---|
| `filter=topsellers` | 2,481 |
| `specials=1` | 10,552 |
| `filter=comingsoon` | 14,030 |
| `sort_by=Released_DESC` | 120,025 |

Verified properties, `filter=topsellers` and `sort_by=Released_DESC` unless noted:

- 50 rows per page; every row an `app` — zero `data-ds-bundleid`, zero
  `data-ds-packageid`, and zero comma-joined `data-ds-appid` values in either sample. With
  `category1=998` an appid extraction is unambiguous.
- Ordering is real: `filter=topsellers` row 1 is Counter-Strike 2 (`730`), and its head
  matches `featuredcategories.top_sellers` from §1.1.
- Pagination works into the tail: `start=2000` returned a full page of 50.
- The walk terminates cleanly: `start=9950` returned HTTP 200 with zero rows.

`filter=popularnew` (371) and `filter=toprated` (173,432) returned nearly the same head as
the unfiltered default, which suggests Steam ignores unrecognised `filter` values and falls
back to relevance ordering. **This was not confirmed.** Both are excluded on that suspicion;
neither is needed.

Only `filter=topsellers` markup was captured as a fixture (`tests/fixtures/steam/search-topsellers-page.json`,
referenced in §7). That `specials=1` and `filter=comingsoon` use the same `search_result_row`
template is assumed, not observed — neither was sampled live.

### 1.5 The risk this carries

This is HTML from an undocumented endpoint — more fragile than the JSON consumed elsewhere
in the app, and the only such parse in the codebase. It is accepted because it is the sole
observed source of a ranked ordering, and because the blast radius is contained: the parse
feeds one table that browse joins against, and a break is detectable (§4).

## 2. Decisions taken

| Question | Decision |
|---|---|
| Ranking source | `search/results` with `infinite=1`; `featuredcategories` retained as a structured cross-check and hero source in M4 |
| Lists tracked | `top_sellers`, `specials`, `coming_soon`, `new_releases` |
| Depth | Top 100 per list per run — 2 pages each, 8 requests total; `--depth` raises it |
| History | None. Current rank only, membership replaced per run |
| Hydration priority | The existing queue orders by best list rank first; no second selection path, no denormalised column |
| Transport | The existing `steamFetchJson`, so the same host limiter, 429 backoff and timeout apply unchanged |

### Why 100 per list

The union across four lists is a few hundred distinct appids, so seeding hydration costs
roughly five minutes rather than 42 hours, and every browse row and hero has real games
behind it. Depth is a flag, not a rewrite: going deeper later is `--depth 500`.

## 3. Schema changes

One table, one migration, in the enum-and-index style already used in `db/schema.ts`:

```ts
export const steamListKind = pgEnum('steam_list_kind', [
  'top_sellers', 'specials', 'coming_soon', 'new_releases',
])

export const steamList = pgTable('steam_list', {
  kind: steamListKind('kind').notNull(),
  appid: integer('appid').notNull().references(() => steamApp.appid, { onDelete: 'cascade' }),
  rank: integer('rank').notNull(),
  fetchedAt: timestamp('fetched_at', { withTimezone: true }).notNull().defaultNow(),
}, (t) => [
  primaryKey({ columns: [t.kind, t.appid] }),
  index('steam_list_rank_idx').on(t.kind, t.rank),
])
```

`rank` is the position within its own list, 1-based, assigned by walk order. The cascade
matches how `game` references `steam_app`.

## 4. `server/steam/store-search.ts`

**Transport.** `steamFetchJson` against `store.steampowered.com`. The envelope is JSON, so
no new HTTP path is introduced: the per-host limiter, `Retry-After` handling and request
timeout from M3 all apply as they stand.

**Parsing.** A Zod schema for `{ success, results_html, total_count, start }` joins the
others in `server/steam/schemas.ts`. From `results_html` the module extracts, per row, only
`data-ds-appid` and its `<span class="title">` text. The markup also carries capsule URLs,
platform flags, release dates and review summaries; none are read. Every one of those fields
arrives properly typed from `appdetails` at hydration time, and parsing them out of markup
would create a second, more fragile source of truth for data already held.

Deviation from the above: the implemented schema stays local to `store-search.ts` instead of
joining `server/steam/schemas.ts` — keeping the one HTML-wrapping envelope next to the only
parser that depends on it is more consistent with the containment argument in §1.5 than
centralising it with the JSON schemas the rest of the client uses.

**The tripwire.** A page yielding zero appids before the requested depth is reached throws.
The failure mode that must never be absorbed silently is a markup change that reads as an
empty list — it would quietly blank every browse row rather than fail. A second tripwire
covers the partial case: fewer rows collected than `total_count` promised also throws, so a
markup change that shrinks pages without emptying them doesn't slip through as a silently
short list.

**List definitions.** One config object keyed by `kind`, holding only the differing query
parameters (`filter=topsellers`, `specials=1`, `filter=comingsoon`, `sort_by=Released_DESC`).
`category1=998`, `count=50`, `infinite=1`, and `cc` / `l` from env are applied centrally, in
keeping with the rule that one place attaches `cc` and `l`.

## 5. `pnpm sync:lists`

`server/catalogue/lists.ts` with a `lists-cli.mts` entry point, mirroring the three existing
jobs. Runs on `DATABASE_URL_UNPOOLED` under advisory lock key `4801003` — the pooled
endpoint grants the same lock to two clients (M3 observations §4). Flags `--depth` (default
100) and `--kind`, in the style of `hydrate`'s `--max-requests` and `--type`.

Per kind: walk pages to depth or exhaustion, then one transaction:

1. Insert any appid absent from `steam_app` as `hydration_state: 'pending'`, using the
   scraped title for the `NOT NULL` name. `app_type` is left null rather than assumed —
   hydration writes the authoritative type to `game.type`, and with rank-first ordering the
   queue no longer depends on `app_type` for these rows.
2. Delete that kind's rows and insert the new membership.

Undocumented until now: a row `sync:lists` inserts this way carries `app_type = NULL`, and
`selectDueApps`'s `--type` filter is `and app_type = ${opts.type}` — so `hydrate --type=game`
skips exactly those rows until the next `sync:catalogue` fills the column from the real app
list. Default (untyped) hydration is unaffected, since it carries no such filter.

The transaction commits only after a complete walk, so a mid-walk failure leaves the previous
membership intact instead of truncating a list to nothing. A stale list beats an empty one,
the same principle as serving stale cache on a Steam error.

## 6. Queue change

`selectDueApps` in `server/catalogue/queue.ts` gains a lateral join for the best rank across
lists, ahead of the existing ordering:

```sql
left join lateral (
  select min(rank) as rank from steam_list where appid = steam_app.appid
) l on true
...
order by l.rank nulls last, (app_type = 'game') desc, steam_last_modified desc nulls last, appid
```

The `where` clause is untouched, so backoff, the `failed` and `unavailable` states, and the
`--type` filter all behave exactly as they do today. Because the join reads current
membership, an app dropping off a list loses its priority on the next select with no
cleanup step.

## 7. Testing

Unit, in the style already used in `tests/`:

- The row parser against a `results_html` fixture captured live during implementation and
  saved under `tests/fixtures/steam/`: appid extraction, title extraction, and the
  zero-row guard throwing rather than returning an empty array.
- URL construction per `kind`.

One addition to `tests/db-integration/queue.test.ts`: a listed app is selected ahead of an
unlisted app that would otherwise sort first. That ordering is the only genuinely risky
piece and no unit test can cover the SQL.

## 8. Out of scope

- Every part of the browse UI. M4 consumes `steam_list`; M3.5 only fills it.
- Rank history and any "climbing the charts" signal.
- Genre and tag lists. M4 filters genres through the normalised `genre` / `game_genre`
  tables, which hydration already populates.
- Scheduling. The job is runnable by hand and in the container, as the other three are;
  wiring a cron caller is a separate decision.

## 9. Verified during implementation

- **Idempotency of `sync:lists`.** Ran it twice against the real database. Both runs produced
  exactly 100 rows per kind (`top_sellers`, `specials`, `coming_soon`, `new_releases`), each
  with `min(rank) = 1` and `max(rank) = 100`, and the union size was identical across both runs
  (365). The row count did not grow on the second run, confirming the delete-and-replace does
  not leak or duplicate rows. Membership itself was not diffed appid-by-appid between the two
  runs (these are live, moving lists, so a diff would not distinguish "not idempotent" from
  "Steam's ranking moved in the ~20 seconds between runs") — the design's actual idempotency
  guarantee, a clean replace with no growth, was verified.
- **Distinct orderings across the four lists.** Verified by comparing appid order pairwise
  across all four kinds after the second sync: `top_sellers` vs `specials` share 35 of 100
  appids but in different rank order (not identical); `top_sellers`, `specials`, `coming_soon`,
  and `new_releases` are otherwise pairwise disjoint (0 appid overlap) between every other pair.
  No two lists were identical in content or order.
- **`appdetails` returning `success: false` for a listed appid.** Not observed in this session.
  All 365 appids in the union were hydrated with `hydrate: attempted=500 ok=500 unavailable=0
  failed=0` across the bounded runs, and a direct query (`hydration_state = 'unavailable' and
  appid in (select appid from steam_list)`) returned 0 rows after every listed appid was
  hydrated. The queue code path for marking an appid `unavailable` was exercised by earlier
  hydration work on this branch but not triggered by any of the 365 listed appids in this run.
  This remains untested against a live `success: false` response for a *listed* appid — it may
  simply not have come up in this particular sample.
- **The actual union size across the four lists at depth 100.** Measured directly:
  `select count(distinct appid) from steam_list` returned **365**, consistent across both sync
  runs. This falls inside the "100 to 400" range the brief predicted and confirms overlap
  between lists is real but partial: 4 × 100 = 400 nominal entries collapsed to 365 distinct
  appids, almost entirely from the 35-appid overlap between `top_sellers` and `specials`.
- **Priority ordering under hydration.** Also verified, beyond what the original four bullets
  asked: before any hydration on this branch, `game` held 27 rows (1 of them listed). After
  `pnpm hydrate --max-requests=25`, `game` held 52 rows (26 listed) — all 25 newly hydrated rows
  came from `steam_list`, confirming the queue selects listed appids first. After
  `pnpm hydrate --max-requests=500`, all 365 listed appids were hydrated (0 pending, 0
  unavailable) and `game` held 552 rows total (365 listed + 187 non-listed), with the run
  spilling into non-listed backlog only once the listed set was exhausted. That run took
  1024.8s (~17 minutes) for 500 requests — 2.05s per app, against a limiter interval of only
  0.833s (1/1.2 req/s). The gap is not the request count: 500 requests at ~1.2 req/s accounts
  for ~417s, leaving roughly 600s unaccounted for by the limiter alone.

  The cause is structural, visible directly in the code, though the round-trip latency itself
  was not independently measured in this session — this is reasoning from the code, not a
  measurement of its parts. `hydrate()` (`server/catalogue/hydrate.ts`) awaits
  `fetchAppDetails`, then `writeHydratedApp`, then `markOk`, strictly serially per appid.
  `writeHydratedApp` (`server/catalogue/hydrate-write.ts`) is one transaction issuing roughly
  a dozen statements — inserts and deletes across `game`, `game_media`, `genre`/`game_genre`,
  `category`/`game_category`, and `price`/`price_history` — each a separate round trip to
  Neon. And `limiter.acquire()` (`server/steam/limiter.ts`) reserves `nextSlot` from `now` at
  the *start* of the next call (`slot = Math.max(now, nextSlot)`), so time spent on the
  database after a fetch is added on top of the 833ms interval rather than absorbed by it.
  Together that leaves roughly 1.2s of fetch latency plus the cost of the serial per-app
  database round trips, not merely "500 requests instead of 365."

  Consequence: a full-catalogue pass at ~2.05s/app is far longer than the ~42 hours quoted at
  the top of this document, which was computed from the limiter interval alone and does not
  hold once per-app database cost is counted. M4 must not plan hydration timelines against
  that 42-hour figure.

## 10. Definition of done

- Migration generated and applied to the real database.
- `pnpm build`, `pnpm lint`, `pnpm typecheck` pass, with output shown.
- A real `pnpm sync:lists` run, with the resulting row counts per kind shown.
- A bounded `pnpm hydrate` run showing listed appids selected first, with the counts before
  and after.
- Each claim in the reply labelled as verified in-session or not.
